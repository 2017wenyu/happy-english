## 方案 B：彻底重构

**核心改变**：
1. **单例模式**：全局只创建一个 `_playCtx`，避免资源竞争和多次创建导致的内存泄漏
2. **懒加载策略**：移除预加载池，改为用户交互时才开始加载，避免提前加载失败影响主流程
3. **错误分级处理**：
   - Level 1：本地失败 → 切换远程（静默）
   - Level 2：远程失败 → 500ms 后重试一次
   - Level 3：重试失败 → 弹 toast "音频加载失败"
4. **生命周期管理**：新增 `cleanup()` 接口，页面 `onUnload`/`onHide` 时统一销毁 Context，避免内存泄漏
5. **销毁保护**：`_isDestroying` 标志位，防止销毁过程中的异步回调触发错误操作

**改动文件**：
- `utils/voice.js`：重写，单例 + 懒加载 + cleanup
- `pages/flashcard/flashcard.js`：移除预加载，改用 `cleanup()`
- `pages/spelling/spelling.js`：移除预加载，改用 `cleanup()`

**预期表现**：
- 资源占用降低（无预加载池）
- 首次点击到播放时间可能略长（懒加载）
- 页面切换/后台时彻底释放资源，避免内存泄漏
- 错误处理更可靠（分级重试）

## 真机首次进入音频播放失败修复

**问题**：第一次进入 flashcard/spelling 页面时，立即调用 `voice.playWordVoice()`，此时分包 mp3 文件可能还没加载完成，触发 onError 显示"音频加载失败"。后续切换卡片就正常了。

**根因**：真机上分包文件首次访问需要时间，而 `playWordVoice()` 是同步调用，文件未就绪时直接播会失败。

**修复**：将自动播放延迟至 `setData()` 完成后 500ms 再触发，确保 DOM 渲染完成 + mp3 文件缓冲就绪。预加载延迟延长至 1500ms，避免与播放冲突。

## voice.js Bug 修复（预加载污染播放状态）

**Bug**：`preloadWordVoice` 会修改 `_currentWord`，导致用户播放当前词时，voice.js 误判"已加载"而直接 play，实际 src 却已是下一个词，于是播出的是下一个词的音频。

**根本原因**：单一 AudioContext 同时承担"播放"和"预加载"两种职责，状态相互污染。

**修复**：将 `_playCtx`（主播放）和 `_preCtx`（预加载）彻底分为两个独立的 InnerAudioContext，各自维护独立的 word 状态，互不干扰。预加载 ctx 出错静默忽略。
